# Latency baseline, 2026-11-07

Run with `perf/latency.mjs`, 5 runs per cell, medians unless noted. All runs come from one Claude Code cloud runner (software GL, egress through a proxy), so absolute numbers are pessimistic. Compare rows with each other, not with field data. Milestones are defined in [`../README.md`](../README.md).

"POIs visible" is `max(mapLoad, poiTilesEnd)`: the walkshed's POI dots cannot draw before the map has loaded, nor before their tiles arrive.

## Is it a regression?

Every build below was rebuilt from its commit with today's identical dependencies (mapbox-gl 3.21.0, React 19.2.4, Vite 8.0.3) and the production token, then served as walksheds.xyz from disk. Same-origin assets skip network throttling in this mode, so mobile numbers here are faster than live.

| Build | Date | Map `load` desktop / mobile | Isochrones start desktop / mobile | POIs visible desktop / mobile |
| --- | --- | ---: | ---: | ---: |
| `4e5a2d7` design system | Jun 20 | 4.20 / 8.72 s | 1.36 / 1.62 s | 4.20 / 8.72 s |
| `8fd921b` embedding | Jul 2 | 4.50 / 8.65 s | 1.43 / 2.10 s | 4.50 / 8.65 s |
| `9ff8400` (#84, before #85) | Jul 12 | 4.57 / 9.34 s | 1.34 / 2.25 s | 4.57 / 9.34 s |
| `f25adc8` (#85) | Jul 17 | 2.81 / 7.07 s | 4.32 / 8.27 s | 4.54 / 10.04 s |
| `d23b8e4` (before multi-city) | Jul 31 | 3.85 / 6.80 s | 4.95 / 8.43 s | 5.33 / 9.72 s |
| `main` + #105 | Nov 7 | 3.76 / 6.80 s | 4.79 / 8.58 s | 5.27 / 10.02 s |

May builds (`6202b32`, `fdb11f5`) used an intro walkthrough and selected no station on `/`, so only their early milestones compare. Their map `load` was 3.3 to 4.0 s desktop and 6.2 to 7.0 s mobile, in line with today.

Verdict: **mostly not a regression.** The bundle grew 43 KB raw in six months and the map's own load time is unchanged. One real but modest regression is #85, which made station selection wait for the map's `load` event (to fix deep-link framing). That serialized the isochrone and POI fetches behind map load, adding about 0.7 s to mobile time-to-POIs. Desktop was roughly flat, because map load sped up once nothing competed with it. The load is slow for structural reasons that predate July (below).

## What-if experiments (live, `--block`)

| Experiment | Map `load` desktop / mobile | POIs visible desktop / mobile | Bytes |
| --- | ---: | ---: | ---: |
| Baseline | 3.57 / 9.47 s | 4.90 / 13.98 s | 2,150 KB |
| Terrain DEM blocked | 2.84 / 8.14 s | 4.57 / 11.07 s | -298 KB |
| Google Fonts blocked | 3.84 / 9.80 s | 4.88 / 14.19 s | -1 KB |

Blocking the terrain tiles is the biggest single measured win: 1.3 s off map load and 2.9 s off POIs on mobile. Blocking Google Fonts brought desktop FCP from 0.39 to 0.25 s and app JS from 0.49 to 0.34 s, and changed nothing measurable on mobile.

## Critical path today (live, mobile cold)

```
0.18  index.js starts ............ 0.92 done
0.99  mapbox-gl.js starts ........ 3.71 done          (could start at 0.18 with a modulepreload)
3.96  style ...................... 5.28 style + iconset
5.40  terrain DEM (298 KB) ....... 8.68 discarded     (competes with vector tiles for 3.3 s)
9.47  map load -> station selected -> 3 isochrone calls ... 10.43
11.37 11 POI tiles (349 KB, 2.35 MB raw) ........... 13.81
```

Nothing on the data side starts before the map finishes loading, even though the stations file (and, on `/`, the default station) is known by about 0.5 s.
